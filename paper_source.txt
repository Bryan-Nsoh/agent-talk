\title{Certificate Talk: Minimal, Proof-Carrying Communication for Two Agents With Private Maps}

\author{Beta Agent Talk Team}

\date{October 9, 2025}

\renewcommand{\headeright}{Draft}
\renewcommand{\undertitle}{Method Note}
\renewcommand{\shorttitle}{Certificate Talk}

\begin{document}
\maketitle

\begin{abstract}
We study two agents with private obstacle maps that must decide whether a safe path exists between a common start and goal. CertTalk is a deterministic dialogue where every exchange ends in a path or cut certificate that both a human and an oracle can replay. Witness bits and fast certificate replies cut typical transcripts to three to five messages while keeping every packet well under 256~bytes. This note focuses on the protocol and implementation details that make those certificates possible.
\end{abstract}

\keywords{certificate protocols \and multi-agent systems \and verifiable communication}

\section*{What this paper proves in one page}
\begin{intuitionbox}
Do not send the whole map; send a small, checkable witness. Like showing a validated boarding pass instead of your entire travel history, a certificate — either a path or a cut — is the least you must show to convince a skeptic. All design choices push toward proofs rather than maps because proofs are tiny, auditable, and settle the question quickly.
\end{intuitionbox}

Every successful conversation ends in one of two small artifacts:
\begin{itemize}
  \item \textbf{PATH\_CERT} proves reachability. It carries a compressed run list (RLE4) and a checksum.
  \item \textbf{CUT\_CERT} proves unreachability. It carries a compressed set of obstacle cells (DELTA16) with one-bit witnesses per cell and a checksum.
\end{itemize}

If the responder can fully validate a proposal, it returns the certificate immediately, the initiator acknowledges it, and the dialogue terminates in three messages.

Because packets are typed JSON with a compact key map and CRCs, the transcripts are both human-readable and easy for an oracle to replay on the union map $U=A\cup B$.

We next define the compact payloads and envelope, show the dialogue choreography, and then formalize the model, agents, and oracle before presenting results. Figures in the next two sections provide a concrete running example and the message flow.

\section{Introduction}
\begin{intuitionbox}
If you want to prove you cannot reach the airport, you do not photograph every street in the city. You show that Highway 101 is flooded and it is the only bridge across the river. Certificates are minimal proofs: instead of revealing everything you know, reveal only what is necessary to settle the question.
\end{intuitionbox}

Robots often make decisions with only a partial view of the world while sharing a narrow communication channel. Consider two agents that hold different obstacle maps of the same environment. They must decide whether a path exists between a shared start and goal without streaming full maps to each other. The straightforward approach is to exchange everything and let a single agent decide. That approach is reliable but expensive in bytes and difficult to audit because the final decision is entangled with the details of fused sensor maps. We explore a different contract where agents trade short, typed messages that carry verifiable evidence about the decision itself. Each conversation ends in a compact artifact that an offline checker can replay on the union map to certify either reachability by a path or separation by a small cut. The goal is to match the reliability of full sharing with fewer bytes and with transcripts that are easy for humans to read.

Our approach draws inspiration from proof-carrying computation. Proof-carrying code replaced trust in a sender with a program that arrives bundled with a machine-checkable proof of safety properties~\cite{Necula1997PCC}. The idea migrated from code to algorithms under the banner of certifying algorithms, where each output includes a witness that an independent checker validates in linear or near-linear time~\cite{McConnell2011Certifying}. We adopt the same philosophy for two-agent coordination: messages are not hints but proofs. A path message is a compressed sequence of steps and a checksum. A cut message is a small set of obstacle cells with per-cell attribution bits that say which agent attests each cell. Either artifact is sufficient for the peer to validate locally and for an oracle to verify globally on the union map.

The problem we study is a close cousin of multi-agent path finding, which typically assumes agents plan trajectories that avoid each other on a shared map~\cite{Sharon2012CBS,Ma2019Prioritized}. We diverge from that setting in two ways. First, our agents do not move simultaneously; they negotiate a single reachability decision. Second, the maps are private and heterogeneous, so the main difficulty is epistemic rather than geometric. This difference shifts the algorithmic focus from joint trajectory search to communication protocols that recover only the information needed to certify a yes or no answer. The verification load then becomes simple. Replaying a candidate path is a linear pass over grid steps, and checking a separator reduces to a standard min-cut disconnectivity check on the potential graph that splits vertices into in/out halves with unit capacities, which is textbook material~\cite{CLRS2009}.

Communication-efficient coordination has deep roots in decentralized control, where agents weigh the value of sending information against the cost of bandwidth and delay~\cite{OliehoekAmato2016}. That line of work clarifies when communication pays off but rarely prescribes the structure of the messages themselves. In parallel, the learning community has studied differentiable inter-agent communication, where policies learn what to transmit through gradient signals~\cite{Sukhbaatar2016CommNet,Foerster2016DIAL,Lazaridou2017Emergent}. Learned protocols can be powerful but are often opaque and difficult to audit. Our contribution complements these directions by proposing a tiny, deterministic protocol in which every packet has human-readable semantics and every conversation culminates in an artifact that a checker can replay. The protocol borrows the accountability of certifying algorithms while preserving the simplicity and small-message footprint required by low-bandwidth links.

Concretely, we present a two-agent dialogue that alternates complete proposals and verifications. When a path is proposed, the responder either upgrades it to a certificate or returns explicit conflicts. When a cut is proposed, the responder validates per-cell attributions and checks that removing the set disconnects start from goal in its own potential graph before certifying it. A minimal probe mechanism resolves ambiguities by asking about a handful of cells once per branch. The resulting transcripts are three to five messages in the common case and remain well under typical per-packet limits. The artifacts are small enough to read at a glance and precise enough for an offline oracle to replay on the union map. The combination yields a communication pattern that is efficient, verifiable, and interpretable.

This work makes five concrete advances. We define a minimal, deterministic dialogue where every run ends in a path or cut certificate with per-cell attribution and CRC guards. We introduce compact, human-legible payloads for paths (RLE4) and cuts (DELTA16 with witness bits) that fit within tight per-packet budgets. We establish a responder fast-path rule that collapses common cases to three messages (proposal, certificate, acknowledgment) without sacrificing verifiability. We design a single-probe reconciliation mechanism that resolves ambiguous separators in one round while keeping transcripts concise. Finally, we provide a reproducible evaluation framework with side-by-side comparisons against Send-All and classical probe-style baselines on a fixed cache, where transcripts and metrics are auditable end-to-end.

Imagine two couriers who must deliver a heavy meal together. Robot~A carries thermal sensors that flag hot hazards such as steam vents and transformer leaks, while Robot~B scans the ground for sinkholes and torn pavement. The city grid is only $10\times 10$ cells in our test bed, yet broadcasting full sensor imagery still costs several kilobytes and multiple seconds per attempt. More importantly, an engineer reading the resulting logs would still not know which obstacles caused the decision to abort or proceed. CertTalk offers a different contract. Each message has a rigid JSON skeleton. Proposals are literal artifacts: either a compressed path from the restaurant to the destination, or a compressed cut that severs the two locations. The responder either returns explicit conflicts or upgrades the proposal to a certificate that the initiator acknowledges. A short transcript suffices to convince a third-party oracle that the decision was correct. Because every field is typed and checksummed, the logs remain compact while revealing the entire reasoning chain.

\section{Algorithmic Building Blocks}
\label{sec:building-blocks}
\begin{intuitionbox}
If you need to cross a small parking lot, you do not pull out GPS and optimize traffic patterns; you walk the shortest path you can see. On a tiny 10x10 grid, BFS is that straightforward walk: the simplest path finder is enough when space is small. We save the cleverness for what matters: the size of the proof you send.
\end{intuitionbox}

Both robots rely on breadth-first search to find shortest paths through their current belief grids. BFS expands the graph layer by layer, guaranteeing optimality when a route exists. On a $10\times 10$ grid the search touches at most one hundred cells and completes in under a millisecond. When no path emerges, the initiator switches to computing a minimum vertex separator using Dinic’s algorithm on the potential graph, where each grid cell becomes a node pair connected by capacity $1$ if blocked or $\infty$ if free. This flow-based approach identifies the smallest set of obstacle cells whose removal would disconnect start from goal.

The resulting paths and cuts must fit within our 256-byte packet limit, which motivates two specialized encodings. Paths are compressed via run-length encoding (RLE4) where two bits capture direction (Up, Right, Down, Left) and six bits store run length, packing up to sixty-three consecutive steps into a single byte. A sequence like “Right×3, Down×4, Right×2, Down×1” fits into four bytes before Base64. Separators use DELTA16 encoding: one absolute $(x,y)$ coordinate followed by signed int8 deltas relative to the previous cell, with restart markers for large jumps. Typical separators of six to twelve cells compress to twelve to twenty bytes.

\begin{intuitionbox}
When two people argue about whether a door is locked, one says "I personally checked" and the other says "okay, I will trust you on that one." Witness bits encode that testimony. Each cut cell carries who vouches for it, so the responder can accept cells it has not seen while still rejecting unjustified ones. Attribution breaks deadlock without streaming full maps.
\end{intuitionbox}

The protocol’s key insight is the witness bit vector. Each separator cell carries one attribution bit: zero means Robot~A detected the obstacle, one means Robot~B supplied it. The responder accepts a certificate if, for every cell, either it sees the obstacle locally or the witness bit credits the peer. This single bit per cell prevents disputes about unseen obstacles while adding negligible overhead. Finally, every payload includes a CRC16-CCITT checksum: \texttt{digest16} guards the raw run or cell bytes, while the envelope checksum \texttt{c} covers the entire canonical JSON packet to catch transmission errors.

\section{Oracle Verification}
\begin{intuitionbox}
When kids argue about whether a board game move was legal, they call a parent who knows the rules and can watch a replay. The oracle is that parent: it sits outside the dialogue, sees the whole board, and checks whether the claimed path or barrier actually holds up.
\end{intuitionbox}

For a path certificate the oracle decodes \texttt{runs}, verifies that the sequence starts at $s$ and ends at $t$, checks that each move is a Manhattan step within bounds, and rejects if any traversed cell belongs to $U$. Optional bookkeeping compares the certified path length to the oracle shortest path to compute the path-gap metric.

For a cut certificate the oracle decodes \texttt{cells}, confirms that the list length matches \texttt{k}, rebuilds witness bits, and rejects if any listed cell is outside the grid or free in $U$. It then removes the cut cells from the potential graph and checks that $s$ and $t$ fall in different components. Only then does the oracle accept the transcript. Because the oracle never interacts with the agents during the dialogue, archived certificates remain valid independently of the execution environment.

Cut acceptance checklist. The responder and the oracle both implement the following checks:
\begin{itemize}
  \item Decode `cells` and confirm $|\text{cells}| = k$; all cells within grid bounds.
  \item For each cell, either it is locally blocked or the `witness` credits the peer.
  \item Remove all `cells` from the potential graph; $s$ and $t$ must become disconnected.
  \item Recompute `digest16` over the raw cell bytes and the envelope CRC `c`; reject on mismatch.
\end{itemize}

\section{Agent Behavior}
\begin{intuitionbox}
If you keep asking "is this road open? what about that one?" you could ask forever. The one probe rule is like saying you get one question about uncertain intersections, then you must commit to a proposal. It forces progress and prevents endless back and forth.
\end{intuitionbox}

Robot~A begins each conversation with an empty belief map and a halo that discourages retrying recently blocked cells. After every message it integrates the peer's evidence. Belief updates are monotone: once a cell is believed blocked it stays blocked, and once it is believed free it stays free. Failed digests are stored so that identical proposals are never retried.

When it is Robot~A's turn to speak, it first constructs a candidate grid by starting from its private mask, adding all cells in the blocked belief set, removing all cells in the free belief set, and temporarily marking the halo cells as blocked. A breadth-first search over this grid either discovers a viable path or proves that no such path exists within the configured horizon. If a path exists, Robot~A serializes it with RLE4 and emits \texttt{PATH\_PROPOSE}. If no path survives, Robot~A computes a minimum separator on the potential graph using Dinic's algorithm with vertex splitting, encodes the separator with DELTA16, adds the witness bits, and emits \texttt{CUT\_PROPOSE}. When a \texttt{NACK} arrives, the conflicts enlarge the belief sets and may trigger a single probe before another artifact is attempted.

Robot~B has a symmetric planner. Upon receiving \texttt{PATH\_PROPOSE} it decodes the run string, reconstructs the path, and checks every step against its map and belief sets. A successful path is immediately returned as \texttt{PATH\_CERT}; a failure yields \texttt{NACK} with the offending coordinates. Upon receiving \texttt{CUT\_PROPOSE}, Robot~B decodes the separator, validates witness bits, verifies local consistency, and ensures that removing the separator from its potential graph disconnects $s$ from $t$. A successful separator is returned as \texttt{CUT\_CERT}. If some cells cannot be justified, Robot~B responds with \texttt{NACK} and highlights those cells so Robot~A can probe or recompute. When Robot~B receives a probe it answers with a packed bitmap describing which queried cells are blocked in its map.

Both robots terminate once they have sent or acknowledged a certificate. The conversation history at that point consists of a handful of JSON objects that capture the entire argument. The next section explains how the oracle replays those objects to provide an independent verdict.

One-probe rule and branch definition. The initiator may issue at most one \texttt{PROBE} per branch. A branch is the contiguous attempt sequence rooted at a unique pair $(\text{last\_nack\_type},\ \text{last\_artifact\_digest})$. Any new artifact digest restarts the branch and re-enables a single probe for that branch.

\section{Encodings and Envelope}
\label{sec:encodings}
\begin{intuitionbox}
When giving directions, instead of saying "right, right, right, down, down, down, down," you naturally say "three rights, then four downs." RLE4 does this for paths. Instead of listing "(2,3), (2,4), (2,5)," you store "start at (2,3), go down twice." It is how we compress repetitive instructions in everyday speech.
\end{intuitionbox}

Every message has the canonical form
\[
  m = \{\texttt{t}:\tau,\;\texttt{p}:\pi,\;\texttt{s}:"v1",\;\texttt{q}:q,\;\texttt{c}:c\}.
\]
The type $\tau$ guards the control flow, \texttt{p} wraps either an artifact or a housekeeping payload, \texttt{q} is a monotone sequence counter per sender, and \texttt{c} is the CRC16-CCITT of the canonical JSON rendering. The same envelope is used for proposals, certificates, NACKs, probes, and acknowledgments.

\subsection*{Paths}
\begin{itemize}
\item \texttt{runs} stores the RLE4 direction stream described in \autoref{sec:building-blocks}. A sequence such as Right×3, Down×4, Right×2, Down×1 fits into four bytes before Base64.
\item \texttt{digest16} is the CRC16 of the raw run bytes. The responder recomputes the checksum before decoding to catch corruption.
\item \texttt{signed\_by} lists which robot issued the certificate. For proposals the field is absent.
\end{itemize}

\subsection*{Cuts}
\begin{itemize}
\item \texttt{cells} carries the DELTA16 encoding of the separator. The initial absolute coordinate plus the delta stream usually compress ten cells into 18--20~bytes.
\item \texttt{k} is a consistency check for the decoder.
\item \texttt{witness} packs one bit per cell. The responder concedes peer-only evidence when the witness credits that peer.
\item The same \texttt{digest16} and optional \texttt{signed\_by} fields play the roles they did for paths.
\end{itemize}

\subsection*{Supporting messages}
\begin{itemize}
\item \texttt{ACK} echoes the digest of the artifact it acknowledges.
\item \texttt{NACK} carries either a bit-mask (for path conflicts) or an explicit list of conflicting coordinates (for cuts).
\item \texttt{PROBE} lists up to six ambiguous cells under the \texttt{wht} (“what”) selector and \texttt{PROBE\_REPLY} returns the blocked/free bits in the same order. Only one probe is allowed per branch.
\end{itemize}

\section{Problem Setting}
\begin{intuitionbox}
A vending machine always gives the same output for the same input, with no randomness and no learning. Our agents work the same way: feed them the same obstacles and queries, get identical responses every time. Determinism makes the protocol debuggable and reproducible under tight byte budgets.
\end{intuitionbox}

Cells are indexed by integer pairs $(x,y)$ with $x$ increasing eastward and $y$ increasing southward. Movement is four-neighbour only; diagonal steps never occur.

We model the environment as a directed grid graph with vertex set $V = \{0,\ldots,9\}^2$ and edges that connect four-neighbour cells. Robot~A knows a private mask $A$ marking thermal hazards. Robot~B knows a private mask $B$ marking structural hazards. The world that matters is the union $U = A \cup B$, yet neither robot ever observes $U$ directly.

The start cell $s$ and goal cell $t$ are common knowledge. The communication channel is perfectly reliable but stingy: each conversation must finish within sixty-four messages, no individual packet may exceed 256 bytes, and the transcript as a whole must stay under 3{,}072 bytes. Messages alternate between robots; Robot~A initiates every run. Success is defined semantically rather than syntactically: a transcript is successful only if it terminates within budget and the final artifact passes the oracle's verification on $U$.

Both robots are deterministic. Their internal state consists of the private map, the growing catalogue of what the peer has claimed, and a small halo that nudges replanning away from recently blocked cells. There is no randomness or machine learning involved. The oracle is an offline checker that never intervenes during the dialogue. It simply replays the final artifact against the union grid and declares acceptance or rejection.

\section{Experimental Setup}
\begin{intuitionbox}
A fixed wind tunnel isolates the effect of a wing. The 1{,}000-instance cache is our wind tunnel: identical air on every run so changes in bytes or rounds reflect the protocol, not the weather.
\end{intuitionbox}

We reuse the publicly released cache \texttt{data/20251008T151417Z\_cache.jsonl}. Each entry records the private masks $A$ and $B$, the oracle reachable flag for $U$, the optimal path length when reachable, and the minimum cut size otherwise. Generating the cache is a single command and takes under a minute on a laptop. The cache seed is fixed so future runs remain comparable.

We evaluate four deterministic policies under identical limits: CertTalk (this work), the baseline Send-All that streams blocked indices in thirty-two–cell chunks, Greedy-Probe which mirrors the early path-versus-probe heuristic, and Responder-MinCut where Robot~B leads with a cut-first strategy. All systems use the compact schema toggle and the same conversation budgets.

For each transcript we log success (oracle accepted certificate), bytes, rounds, path gap, cut gap, and the share of conversations ending in a certificate (equal to success for deterministic systems). Medians and 95\% bootstrap intervals are reported across the full cache. Because every transcript is archived, the statistics are easy to audit: recomputing the median bytes is a matter of streaming the JSONL file.

\section{Ablations and Evolution}
Witness bits and targeted probes. The 2025-10-08 run without witness bits stalled at a median of $3.1$~KB and $21$ rounds. Introducing witness bits and the single-probe rule dropped CertTalk and Greedy-Probe to $947$~bytes and $7$ rounds while preserving $>99.9\%$ success. Conflicting cells now resolve on the very next attempt rather than oscillating.

SCHEMA handshake removal. Eliminating the two-message SCHEMA preamble pushed the median down to $653.5$~bytes and kept rounds at $7$. No correctness regressions were observed; the same single probe still sufficed on the ambiguous cuts.

Compact schema everywhere. Applying the compact key map to all systems closed the final gap. CertTalk’s median bytes now sit at $468.5$ with a median of five rounds, Greedy-Probe mirrors the same numbers, and Send-All benefits as well (median $364$~bytes). The responder-led min-cut baseline remains unchanged because it does not rely on compact keys.

Future drafts will add a small bar chart summarising the byte reductions from each toggle. The text above already records the concrete medians for reproducibility.

\section{Limitations}
\begin{intuitionbox}
The protocol deliberately targets a narrow, fully deterministic setting; several assumptions would need adjustment for broader deployments.
\end{intuitionbox}

\begin{itemize}
\item \textbf{Reliable channel.} Messages never drop or reorder in our experiments. A lossy link would require replay buffers or per-message signatures.
\item \textbf{Two agents only.} CertTalk currently handles a single initiator and responder. Extending to $n$ agents would require a richer notion of witness attribution and shared sequence numbers.
\item \textbf{Small grids.} The $10\times10$ benchmark keeps planning trivial so that communication dominates. Larger maps are likely to need chunked certificates or multi-stage artifacts.
\item \textbf{No privacy model.} Witness bits expose which robot attested each obstacle. Protecting sensor privacy would require masking or cryptographic commitments.
\end{itemize}

\section{Reproducibility}
\begin{intuitionbox}
All artifacts live in the repository; reproducing the study is a sequence of four commands once \texttt{uv} is installed.
\end{intuitionbox}

\begin{enumerate}
\item Create the environment and install the package:
\begin{lstlisting}[language=bash]
uv venv
source .venv/bin/activate
uv pip install -e .[analysis]
\end{lstlisting}

\item Regenerate the 1{,}000-instance cache:
\begin{lstlisting}[language=bash]
uv run python -m agent_talk.env.generator \
  --out data/20251008T151417Z_cache.jsonl \
  --n 1000 --size 10 --seed 123
\end{lstlisting}

\item Re-run all four systems under the SCHEMA-free configuration:
\begin{lstlisting}[language=bash]
uv run python -m agent_talk.runners.batch_eval --cache data/20251008T151417Z_cache.jsonl --system certtalk --out runs/20251009T201009Z_certtalk.jsonl
uv run python -m agent_talk.runners.batch_eval --cache data/20251008T151417Z_cache.jsonl --system sendall --out runs/20251009T201024Z_sendall.jsonl
uv run python -m agent_talk.runners.batch_eval --cache data/20251008T151417Z_cache.jsonl --system greedyprobe --out runs/20251009T201034Z_greedyprobe.jsonl
uv run python -m agent_talk.runners.batch_eval --cache data/20251008T151417Z_cache.jsonl --system respondermincut --out runs/20251009T201043Z_respondmincut.jsonl
\end{lstlisting}

uv run python -m agent_talk.analysis.metrics \

  --out runs/20251009T201059Z_summary.csv
\end{lstlisting}
\end{enumerate}

\section{Conclusion}
\begin{intuitionbox}
A handful of typed messages can replace full map exchange if the messages themselves carry proofs. CertTalk demonstrates the idea in a controlled setting, yielding transcripts that humans and machines can audit alike.
\end{intuitionbox}

We presented CertTalk, a certificate-carrying protocol for two agents with private occupancy grids. Witness bits and fast certificate replies collapse dialogue length, while compact encodings keep every packet well under $256$ bytes. On a reproducible 1{,}000-instance benchmark CertTalk matches the reliability of the Send-All baseline, spending about one hundred extra bytes so the transcript itself becomes the path-or-cut witness. Send-All streams raw indices that must be recomposed into the union map; CertTalk hands over the finished argument. We hope this work encourages the broader community to treat communication products as proofs and to demand the same auditability from robotic dialogues as we do from certifying algorithms.
